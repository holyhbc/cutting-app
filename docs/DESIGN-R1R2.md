## 二、R1 员工记忆方案

### 机制

```
首次填工号 A005
   → 服务端查 ygzl 校验（离职即拒）
   → 签发令牌 token（secrets.token_urlsafe(32)）
   → 存 worker_session 表
   → token 存手机 localStorage

以后扫码：页面读 localStorage 的 token
   → GET /api/whoami 验证
   → 有效则显示「张诚 A005 [切换]」，跳过工号输入
   → 每次验证都重新查 ygzl，离职即时失效
```

### 表结构

```sql
CREATE TABLE IF NOT EXISTS worker_session (
    token      TEXT    PRIMARY KEY,
    ygno       TEXT    NOT NULL,
    created_at TEXT    NOT NULL,
    expires_at TEXT    NOT NULL,     -- 到期即失效
    last_seen  TEXT    NOT NULL,
    device     TEXT    NOT NULL DEFAULT ''
);
CREATE INDEX IF NOT EXISTS ix_session_ygno ON worker_session (ygno);
```

**要点**：
- 令牌**明文存储**即可（车间应用，非金融级）；但 `SYNC_TOKEN` 那类系统级令牌仍走环境变量不进库
- 每次使用都**重新查 `ygzl`**：员工当天离职，令牌立刻作废
- 定期清理过期记录

### 安全权衡（必须说清）

| 风险 | 缓解 |
|---|---|
| 手机被同宿舍/工友拿到，冒名报工 | 令牌**有有效期**（见决策 Q1），隔天失效；页面上「张诚 A005」常驻可见，工友一看就知道是谁 |
| 一台手机多人共用 | 提供**显眼的「切换」按钮**，切换需确认 |
| 令牌被复制 | 限定单设备；不跨设备同步 |

**关键兜底**：首次报工直接生效，但**改量必须主管审批**（D-005）。
所以冒名的最坏后果是"多报一次首次数量"，金额有限，且事后可查 `jfgz` 的 `ygno`。

> ⚠️ 前提：车间没有密码习惯，工号本身就是身份凭证。
> 若你希望加 PIN 码，见决策 Q3。

## 三、R2 工序记忆方案

### 记忆粒度：两级回退

```
① 查 (工号, 定单, 层, 扎)  → 精确记忆：这扎上次做的哪道
② 查不到则查 (工号, 定单)  → 款式记忆：这一单他一直在做同一道
③ 都没有 → 不预选，让他自己点
```

**为什么两级**：
- 流水作业里一个工人往往连续几扎做同一道 → ②命中率高
- 但同一扎内偶尔换道（如换人接手）→ ①保证这种情况下不会记错

### 表结构

```sql
CREATE TABLE IF NOT EXISTS worker_pref (
    ygno      TEXT    NOT NULL,
    scope     TEXT    NOT NULL,   -- 'bundle' 或 'zdno'
    zdno      TEXT    NOT NULL,
    cc        INTEGER NOT NULL,
    zh        INTEGER NOT NULL,
    gx        INTEGER NOT NULL,
    updated_at TEXT   NOT NULL
);
-- 同一粒度下只保留一条偏好
CREATE UNIQUE INDEX IF NOT EXISTS ux_pref_bundle
    ON worker_pref (ygno, scope, zdno, cc, zh);
```

**要点**：偏好是**覆盖式**的，不记历史。只留最新一道。

### 数量预填规则

预填**该工序的剩余应做数**，而不是"上次报了多少"。

原因：工人这次要补的是**没做完的部分**。预填上次数量会导致反复报同样的数。

```python
remain = plan_qty - reported_qty(该扎该工序)
input.value = remain if remain > 0 else ""
```

### 边界情况

| 情况 | 处理 |
|---|---|
| 记忆的那道工序**已做满** | 不预选，页面提示「上次做的『衣线头』已做完，换一道?」 |
| 这扎只有一道工序 | 直接预选，无需用户操作 |
| 工人**换了工序** | 手动点其他工序即可，同时**覆盖记忆**（下次记住新选择） |
| 该定单工序很多（>10） | 记忆的项**自动滚动到可见位置** |

## 四、接口

### 新增 3 个

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/login` | `{ygno}` → 校验 `ygzl`，签发 `{token, ygname, expires_at}` |
| `GET` | `/api/whoami` | 读 `Authorization: Bearer <token>` → `{ygno, ygname}` 或 401 |
| `POST` | `/api/logout` | 删除该 token |

### 改动 2 个

| 方法 | 路径 | 改动 |
|---|---|---|
| `GET` | `/s/{short_id}` | 页面携带 token 时直接渲染「已登录 + 预选工序 + 预填数量」 |
| `POST` | `/api/report` | 成功写入后**更新** `worker_pref` 记忆 |

`/api/report` 接受可选的 `token` 字段；有则跳过工号输入，用令牌里的 `ygno`。

## 五、页面改造要点

1. **登录态卡片**：有 token 时把「① 你的工号」输入框换成
   `👤 张诚 A005  [切换]`，高度相同避免跳动
2. **工序预选**：加 `sel` 高亮 + 滚动到可视区
3. **数量预填**：JS 从 `data-remain` 读取
4. **离线/令牌失效兜底**：token 失效时**静默回退**到工号输入框，不弹错误打断
5. **切换流程**：点「切换」→ 清 token → 聚焦工号输入框 → 重新登录

前端仍用原生 JS（保持零依赖），localStorage 存 token。

| 风险 | 缓解 |

## 九、需要你确认的 3 件事

### Q1 令牌有效期多久？
| 选项 | 效果 | 风险 |
|---|---|---|
| **12 小时** | 覆盖一个班次 + 加班 | 同宿舍工友当天可能冒用 |
| **24 小时** | 第二天要重填 | 较低 |
| **7 天** | 一周只填一次 | 冒名窗口大 |

**建议 24 小时** —— 第二天开工重新填一次，换来较低冒名风险。

### Q2 记忆粒度？
- **A. 只要「工号+定单」**（简单，覆盖 90% 场景）
- **B. 两级：先扎、再定单**（推荐，稍复杂但更准）

**建议 B**。

### Q3 要不要给工号加密码？
- **A. 不加**，工号即身份（车间惯例，工人不用记密码）
- **B. 加 PIN**（如 4 位数字），换人时必须输入

**建议 A** —— 因为改量已需主管审批，风险有兜底；加 PIN 会让操作变繁琐，工人抵触。

## 十、已修复：多扎多色多数量问题 ✅

**问题**：`hbc-print` 界面的「尺码数据」表模型是
「同一颜色尺码下**每扎件数相同**」，用户填一次「颜色+尺码+每扎件数+手数」即平铺给所有扎。

但真实数据是**一扎一色一码、数量各异**：
```
269830套装1-22  扎1火山灰264  扎2奶茶棕406  扎3棕咖42  扎4黑灰250
```
用手填的「每扎406」会印错**全部 44 个标签**的件数和颜色。

**修法**（不改 `build_number_assignments` 的平铺逻辑）：

新增 `load_bundle_color_data(zdno, cc=None)`，从 `jfzd2` 按
`(zdno, cc, zh, YS, CM)` 逐行读取，每扎产出一行 `pieces=1` 的记录，
顺序与扎号一致，直接喂给 `build_barcode_items`。

界面新增 **「📥 从数据库读取」** 按钮：填好定单前缀与起止编号后一键填充尺码表，
并同步开始/结束编号、弹出明细供人工核对。

**验证**：`269830套装1-22` 四扎的颜色与件数逐个与数据库比对，
**不一致 0 处**；44 个标签的二维码 4 个短ID 全部正确对应。
