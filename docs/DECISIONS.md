## D-001 扫码粒度 = 一扎（ZH），不是一卷

- **决定**：二维码标识到「扎」级别，工人在扫码后**自己选择本次做的工序**。
- **理由**：一个扎通常要多人分工协作，工序不固定；二维码上印死工序会导致工人扫错。
- **影响**：二维码 payload 只含 `ZDNO + CC + ZH`，不含工序号。

---

## D-002 二维码必须包含 CC

- **决定**：二维码标识 = `ZDNO + CC + ZH` 三元组。
- **理由**：数据核查发现 **59 组 `(ZDNO, ZH)` 在不同 CC 下重复**，只用 `ZDNO+ZH` 会张冠李戴。
- **影响**：`gen_short_id(zdno, cc, zh)` 必须三参数，缺 CC 视为 bug。

---

## ⚠️ D-003 条码来源标记 —— 【已作废】

- **原决定**：复用 `jfgz.barcode` 字段，`1` = 扫码，`0` = 人工。
- **❌ 作废原因**：实库核查发现 `barcode=1` 已有 **125333** 行、`barcode=0` 有 2815 行，
  且同月内两值交替出现。该字段**早已被历史业务占用**，语义未知（疑似"已审核/已记账"）。
- **后果**：若拿来当扫码标记，会污染 12.5 万条历史统计口径。
- **替代方案（待定）**：
  - a) 新增独立来源字段（如 `jfgz.src`），不动 `barcode` —— **推荐**
  - b) 新建扫码专表，报表层 UNION
  - c) 先查明 `barcode` 真实语义后再决定
- **当前状态**：⏸ **冻结，禁止使用**。

## ⚠️ D-004 gzdate 存完整 datetime —— 【有风险，待复核】

- **原决定**：`gzdate` 写完整日期时间（如 `2026-10-09 14:30:00`）。
- **⚠️ 核查发现**：现有 **12.8 万条全部是 `00:00:00`**（纯日期）。
- **风险**：新数据带时分秒，会与历史不一致，可能影响现有工资计算 / 按日聚合报表。
- **⏸ 状态**：待用户确认 —— 是坚持写完整时间，还是跟随历史只写日期。
- **技术备注**：SQL Server 2000 无 `datetime2`，只能用 `datetime`（3.33ms 精度，够用）。

## D-005 改量必须主管审批

- **决定**：
  - **首次报工** → 直接生效
  - **修改已报数量** → 生成待审批记录，主管通过后才落库
- **理由**：数量直接影响计件工资，错报会造成实际损失。
- **影响**：需要一张审批表 + 审批状态机；不允许直接 UPDATE 已生效的 `jfgz`。

---

## ⚠️ D-006 数量上限规则 —— 【基准字段错误，待重定】

- **原决定**：
  1. 同一 `(扎, 工序)` 下全体员工合计不得超过 `jfzd2.JS`
  2. 单人修改上限 = `应做数 − 他人已报 + 自己已报`
- **❌ 核查发现两个问题**：
  1. `jfzd2` **没有工序字段**，无法表达"该工序应做数"。它是「扎 × 颜色 × 尺码」。
  2. `jfzd2.JS` 合计 9,971,939，而 `jfgz.js` 合计 48,078,613（**4.8 倍**），
     说明 `jfgz.js` 是跨工序累计量，不受 `jfzd2.JS` 总量约束。
- **⏸ 状态**：上限基准待重新确认后才能实现。
- **仍成立的部分**：上限校验本身、同事务串行化、禁止超额，这三点不变。
- **理由**：防止多人重复报工导致超做。
- **影响**：报工与改量接口都要做实时的合计校验，**在事务内加锁/串行化**。

## D-007 主管名单走环境变量

- **决定**：`SUPERVISORS="A001,A003"`，启动时读取，不写死在代码里。
- **理由**：车间主管会调整，避免每次改代码。
- **影响**：新增审批页面需要鉴权中间件。

## D-008 审批通知先做站内角标

- **决定**：第一版**不接 webhook / 企业微信推送**，只在页面上显示待审批数量角标 + 书签。
- **理由**：先跑通主流程，推送是锦上添花，且 webhook 需要内网穿透。
- **影响**：预留通知接口，但不在阶段 1 实现。

---

## D-009 部署拓扑：VPS 不连 SQL Server

- **决定**：
  - VPS 只跑扫码网页 + 暂存数据库（SQLite/Postgres）
  - SQL Server **不开公网端口**
  - 局域网内的 hbc-print 电脑**主动轮询同步**到生产库
- **理由**：SQL Server 2000 无公网暴露面，主动出站比被动入站安全得多。
- **影响**：存在同步延迟；需要处理断网重传与幂等去重。

---

## D-010 过渡期标签同时保留条码和二维码

- **决定**：新标签在条码右侧空白处加 **13mm 二维码**，**条码继续保留**。
- **理由**：老扫码枪/旧流程不能一次性切断；过渡期内两种方式并行。
- **影响**：需确认标签尺寸放得下；放不下则缩放或加长标签纸。

---

## D-011 标签上的条码格式暂不改动

- **决定**：阶段 0 **不改** `make_full_barcode()`，保持 13 位。
- **理由**：改 ZDID 位宽（4→5 位）会把 Code128 变 14 位，需先确认扫码枪兼容性。
- **影响**：二维码走独立短 ID，不依赖条码格式，两者互不干扰。

---

## D-012 明细表写入与保存解耦

- **决定**：`jfzd2_detail` 由**独立按钮**写入，执行保存工单时**不自动写**明细。
- **理由**：用户要求可分批补录、可预览、可撤销。
- **影响**：
  - `📝 写入明细` — 读当前界面数据
  - `📊 补录明细表` — 读历史 `jfzd2`
  - 汇总工单（无工序行的）补录时**必须拒绝**
