## D-001 扫码粒度 = 一扎（ZH），不是一卷

- **决定**：二维码标识到「扎」级别，工人在扫码后**自己选择本次做的工序**。
- **理由**：一个扎通常要多人分工协作，工序不固定；二维码上印死工序会导致工人扫错。
- **影响**：二维码 payload 只含 `ZDNO + CC + ZH`，不含工序号。

---

## D-002 二维码必须包含 CC

- **决定**：二维码标识 = `ZDNO + CC + ZH` 三元组。
- **理由**：数据核查发现 **59 组 `(ZDNO, ZH)` 在不同 CC 下重复**，只用 `ZDNO+ZH` 会张冠李戴。
- **影响**：`gen_short_id(zdno, cc, zh)` 必须三参数，缺 CC 视为 bug。

## ✅ D-003 条码来源标记 —— 【已确认有效】

- **决定**：复用 `jfgz.barcode` 字段。
  - `barcode = 1` → **扫条形码**录入（扫码报工）
  - `barcode = 0` → **系统手动输入**录入

- **影响**：新扫码数据写 `barcode = 1`，与历史口径一致，**无需新增来源字段**。

## ✅ D-004 gzdate 存完整 datetime —— 【已确认】

- **决定**：`gzdate` 写**完整日期时间**（如 `2026-10-09 14:30:00`）。
- **来源**：用户 2026-10-09 确认（知晓历史为 `00:00:00` 后仍选择写完整时间）。
- **实库现状**：现有 12.8 万条**全部是 `00:00:00`**（纯日期）。
- **⚠️ 已知影响（接受）**：
  - 新旧数据格式不一致，跨历史区间的"按日聚合"需用 `CAST(gzdate AS DATE)` 语义取日期部分
  - 现有工资/报表若依赖 `gzdate = 某日0点` 做等值比较，新数据会漏匹配 → 需改用日期范围比较
  - 好处：能看出具体报工时刻，便于排查补录、错报、并发重复报工
- **实现要求**：
  - SQL Server 2000 无 `datetime2`，用 `datetime`（3.33ms 精度，足够）
  - 写入前统一格式化，**时区以服务器本地时间为准**
  - 同步程序传输时用 ISO 格式字符串，避免驱动隐式转换丢精度
- **对账查询写法**（跨新旧数据安全）：
  ```sql
  -- 正确：按日期范围
  WHERE gzdate >= '2026-10-09' AND gzdate < '2026-10-10'
  -- 错误（会漏掉新数据）
  WHERE gzdate = '2026-10-09'
  ```

## D-005 改量必须主管审批

- **决定**：
  - **首次报工** → 直接生效
  - **修改已报数量** → 生成待审批记录，主管通过后才落库
- **理由**：数量直接影响计件工资，错报会造成实际损失。
- **影响**：需要一张审批表 + 审批状态机；不允许直接 UPDATE 已生效的 `jfgz`。

## ✅ D-006 数量上限规则 —— 【已修正并实证】

- **原决定**：
  1. 同一 `(扎, 工序)` 下全体员工合计不得超过 `jfzd2.JS`
  2. 单人修改上限 = `应做数 − 他人已报 + 自己已报`
- **✅ 核查后修正（2026-10-09）**：
  - `jfzd2` 无工序字段 → 应做数按 **`(zdno,cc,zh)` 聚合 `SUM(JS)`**，
    该扎可能有多行（颜色 × 尺码），**不能取单行**。
  - 校验维度为 `(zdno, cc, zh, gx)`，即"一扎的某道工序"。
- **✅ 已实证**：每组 `(zdno,cc,zh,gx)` 的已报合计 ÷ 该扎应做数 **倍率 = 1.00**（抽样全为 1.00）。
  - 未超 127300 组，超额 319 组（0.25%）
  - 也解释了 `jfgz.js` 总量是 `jfzd2.JS` 的 ~4.8 倍：**每道工序都报整扎数量**，属正常，非数据异常。
- **最终规则**：
  ```sql
  SUM(jfgz.js) WHERE zdno=? AND cc=? AND zh=? AND gx=?   -- 已报
    <= SUM(jfzd2.JS) WHERE zdno=? AND cc=? AND zh=?     -- 应做（按颜色尺码求和）
  ```
- **单人改量上限** = 应做数 − 他人已报 + 自己已报
- **理由**：防止多人重复报工导致超做。
- **影响**：报工与改量接口都要做实时的合计校验，**在事务内加锁/串行化**。

## D-016 登录标识：工号 或 手机号，二选一都接受

- **决定**：登录时填「工号 **或** 手机号」，两者都能用；PIN 4 位。
- **理由（实库核查）**：`ygzl` 里可用于第二因子的字段几乎全空 ——
  `con_tel` 仅 1/116、`ygsend1~6` 为 0（且是 decimal 是金额不是号码）、
  `id_no` 0、`cardid` 0。所以**不能把手机号当作已有的登录凭证**。
  而车间实况是"有些工人记不住工号，但记得住手机号" → 两者都收。
- **重名**：`ygname` 有 2 组重名（林和女×2、杨尚听×2），
  故**一律用工号作主标识，姓名只作显示**，页面显示 `张诚（A005）`。
- **存储**：手机号归一化（只留数字、剥 `+86`），UNIQUE 索引防重复。

## D-017 初始 PIN = 手机号后 4 位

- **决定**：初始 PIN 取手机号后 4 位，PIN **只存哈希+盐**，不存明文。
- **理由**：工人只需记住**一样东西** —— 自己的手机号，不必额外记 PIN，
  也不用班组长发 116 张卡片。
- **⚠️ 已知弱点**：知道完整手机号的人即可登入，强度约等于"要同时知道手机号"。
  相比"只知道工号"是提升，但不是密码级。
- **兜底**：① 首次报工直接生效，但**改量须主管审批**（D-005），
  冒名最坏后果限于多报一次首次数量，事后可查 `jfgz.ygno`；
  ② 页面常驻显示姓名+工号；③ `must_change` 提示工人改成自选 4 位。
- **激活范围**：116人中仅约 30 人在裁剪车间，其余 `active=0` 不得登录。
  `active` 由班组长控制，与 `ygzl.ygout`（人事控制离职）职责分离。

## D-018 令牌长期有效，靠每次查 ygzl 兜底

- **决定**：登录令牌**无到期日**（远期），"直到员工离职"由**每次使用都查
  `ygzl`** 实现，而非人工删令牌。

- **配套**：提供显眼的「切换」按钮，共用手机时上一位的影响可被消除。

## D-013 工序与单价的权威来源是 `jfdj`

- **决定**：一扎可做的工序 = `SELECT gx, gxname, dj FROM jfdj WHERE zdno=? AND gx BETWEEN 1 AND 18`
- **理由**（实库核实）：
  - `jfdj` 结构：`(zdno, gx, gxname, dj, mdate, oksl, remark)` —— **既含工序也含单价**
  - `jfdj.gx` 是**定单内的工序序号**（1~18），不是全局工序ID
  - 工序序号越小行数越多（工序1 有 10418 行，工序15 仅 148 行），符合"多数款式工序少"
  - 一个定单通常 9 道工序，如 `261069套装185-188` = 加条/压下摆/手脚口/扎口/印衣标/衣线头/裤线头/包胶/压胶
- **不用** `jfdjgxk`（48 条工序库，含单价但与实际排产无直接关联）
- **必须加 `gx BETWEEN 1 AND 18`** —— 有 5 个定单存在 gx 为 NULL 或 >18 的脏数据（`9712套装*` 各 639 行）

## D-014 工序名称不能等值匹配

- **决定**：统计/匹配工序时**不得**用 `gxname = ?` 精确比较。
- **理由**：历史写法不统一，同一工序有多种写法并存：
  - `印商标` / `印衣标`
  - `上安纶` / `上氨纶`
  - `四针六线-衣` / `四针六线衣` / `四针六线-套`
- **影响**：需要稳定口径时，用 `gx`（序号）+ `zdno` 组合，或另建别名映射表。
  **不要**用 `MAX(gxname)` 之类的聚合去"猜"名称（会得到错误结果）。

## D-015 核查结论不得臆断，必须确认

- **决定**：对数据库字段语义的判断，若**不能从数据本身唯一确定**，必须向用户确认后才能写入决策。
- **来源**：2026-10-09 我犯过两次错：
  1. 仅凭"`barcode` 两个值行数都很多"就臆断"语义未知、禁止使用" → 用户澄清后证明我错了
  2. 用 `GROUP BY gx` + `MAX(gxname)` 判断工序编号，得出的"`gx` 不可信"结论完全是**查询方式的假象**
- **正确做法**：
  - 抽样要看**单行原始数据**，不要只看聚合结果
  - 涉及业务语义（如"扫码/手工""已审核"）时**必须问用户**，数据本身无法证明
  - `MAX()`/`MIN()` 取中文文本会按字典序产生误导性结果（"扎口" > "包胶"），不可用来推断字段语义
- **影响**：本文件所有 ⚠️ 条目在获得用户确认前不得当作定论。
