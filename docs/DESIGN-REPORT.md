## 三、架构：数据怎么到 VPS

### 约束

**VPS 不连 SQL Server**（D-009：局域网电脑主动出站，SQL Server 不暴露公网）。

### 方案：报表数据也走「局域网推送」

```
局域网电脑（能连 SQL Server）
   │
   │  1) push_reports.py  读 jfgz（增量 or 全量）
   │  2) 推 JSON 到 VPS
   ↓
VPS  /api/reports/push  (Bearer 鉴权)
   ↓
SQLite 本地表 jfgz_report
   ↓
   ├─ 手机 /report        （读 SQLite）
   └─ 桌面 zdno_edit       （直连 SQL Server，不走 VPS）
```

### 体积评估

```
全量 130633 行 × 约 95 字节 ≈ 11.8 MB
增量（每天）≈ 几十 KB ~ 2.5 MB
```

实测快照推送 22.7 MB 用 7.4 秒，**11.8 MB 完全在能力范围内**。

### 增量策略

`jfgzid` 是 IDENTITY，**有空洞**（最大 131898 但只有 130633 行）。
所以增量用 `WHERE jfgzid > 上次最大值`，**靠最大值推进，不用行数**。

⚠️ 但要防一种情况：如果 `jfgzid` 被重置或数据被删，增量会漏。
**对策**：VPS 记录已同步的最大 `jfgzid`；同步器每次也报总数，
两者对不上时告警并建议全量重推。

## 四、本地表设计

```sql
-- 报工明细（报表的唯一数据源）
CREATE TABLE IF NOT EXISTS jfgz_report (
    jfgzid   INTEGER PRIMARY KEY,     -- 对齐 SQL Server，便于对账
    gzdate   TEXT    NOT NULL,        -- 完整日期时间
    gzday    TEXT    NOT NULL,        -- 日期部分 YYYY-MM-DD，聚合用
    ygno     TEXT    NOT NULL,
    zdno     TEXT    NOT NULL,
    gx       INTEGER NOT NULL,
    gxname   TEXT    NOT NULL DEFAULT '',
    cc       INTEGER,
    zh       INTEGER,
    js       INTEGER NOT NULL,
    dj       REAL    NOT NULL DEFAULT 0,
    je       REAL    NOT NULL DEFAULT 0,
    barcode  INTEGER NOT NULL DEFAULT 1
);
CREATE INDEX IF NOT EXISTS ix_rep_day  ON jfgz_report (gzday);
CREATE INDEX IF NOT EXISTS ix_rep_ygno ON jfgz_report (ygno, gzday);
CREATE INDEX IF NOT EXISTS ix_rep_zdno ON jfgz_report (zdno, gx);

-- 同步水位
CREATE TABLE IF NOT EXISTS sync_meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
-- key='jfgz_max_id'  value='131898'
-- key='jfgz_rows'    value='130633'
```

### 为什么要存 `gzday`

`gzdate` 存的是完整日期时间（新数据）或 `00:00:00`（历史数据）。
按日期聚合时统一取前 10 字符，**新旧数据都能正确分组**。

```python
gzday = str(gzdate)[:10]     # '2026-10-10'
```

⚠️ 这也避免了 D-004 提到的"新旧格式不一致"问题。

## 五、三类报表

### 报表 A：生产进度看板（给主管/管理层）

**看什么**：某定单裁了多少、还剩多少、哪些工序做完了、谁在做。

| 指标 | 计算 |
|---|---|
| 应做数 | `SUM(jfzd2.JS)` 按 (zdno,cc,zh) |
| 已报数 | `SUM(jfgz.js)` 按 (zdno,cc,zh) |
| 完成率 | 已报 / 应做 |
| 各工序进度 | 按 gx 拆开看 |
| 异常提示 | 超量、做了一半、无人报工 |

**视图**：
```

  扎1 火山灰   264件  ▓▓▓▓▓▓▓▓ 100%  ✅
  扎2 奶茶棕   406件  ▓▓▓▓▓░░░  62%
  扎3 棕咖      42件  ░░░░░░░░   0%  ⚠️ 无人报工
  扎4 黑灰     250件  ▓▓▓▓▓▓▓▓ 100%  ✅

  打洞纽扣  962/962  100%
  裤线头    962/962  100%
  压下摆    458/962   48%  ⚠️
```

### 报表 B：计件工资报表（给财务）

**看什么**：某员工某时间段做了多少件、多少钱。

```sql
SELECT ygno, gzday, gx, SUM(js), SUM(je)
FROM jfgz_report
WHERE ygno=? AND gzday BETWEEN ? AND ?
GROUP BY ygno, gzday, gx
```

**三种口径**（必须让财务选，口径不同结果差很多）：

| 口径 | 公式 | 说明 |
|---|---|---|
| A. 按实报 | `SUM(je)` | 报多少算多少 |
| B. 按工序单价重算 | `SUM(js) × jfdj.dj` | 用**当前**单价算历史，与口径 A 有差异 |
| C. 按应做封顶 | `MIN(SUM(js), SUM(应做))` | 防止超报虚增工资 |

⚠️ 实库有 **320 组超量**（占 0.25%），口径 C 是否需要请财务定。

**汇总视图**：
```

工号   姓名    工序     件数     金额      报工次数

A001  陈秋雪  裤线头      8,120   8,936.00     96
A001  陈秋雪  ──小计──   20,460  24,978.00    224
...
合计                    186,432  243,891.00   1,842
```

## 十三、SQL Server 2000 的三个坑（实测踩到）

写这个报表时踩到的，**以后改 SQL 务必记住**：

| 坑 | 现象 | 正确写法 |
|---|---|---|
| `TOP` 不能带括号 | `TOP (5)` 报语法错误 | `TOP 5`，括号是 2005+ 才支持 |
| `TOP` 不能用占位符 | `TOP (?)` 报语法错误 | 内联整数（来自用户输入时要转 int） |
| `GROUP BY` 不接受表达式 | `GROUP BY CONVERT(...)` 报错 | 先在派生表里算好，外层再 GROUP BY |

另外 `plan` 是 SQL Server 保留字，列名要避开（用 `plan_num`）。

还有：`ygzl` 的姓名列是 **`ygname`**，不是 `xm`。
